## P1 · 账号生命周期管理

**状态:** 📋 待实施（2026-01-25 识别）
**涉及模块:** users / auth / mobile has-web

### 背景
当前用户状态只有 `1=启用 / 0=停用` 两态，缺少完整的账号生命周期能力。

### 已识别的问题

1. **物理删除导致数据孤儿（严重）**
   - `backend/src/modules/users/users.service.ts` 的 `remove()` 使用 `userRepo.remove(user)` 直接删除 `users` 表记录
   - 审计日志、通知记录、占卜记录、家庭关系等均持有 `user_id` 外键引用，删除后这些记录指向不存在的用户
   - 不可恢复，误删只能依赖数据库备份
   - 审计系统核心价值是"谁在何时做了什么"，用户被删后该信息不可追溯

2. **停用缺少留痕**
   - `disable()` 仅将 `status` 置 0，未记录操作人、操作时间、停用原因
   - 缺少状态变更历史，出现争议时无法追溯

3. **缺少终态**
   - 无"已注销"状态，无法区分"临时停用"与"永久注销"

### 建议方案

**状态机扩展**

| 状态值 | 含义 | 可恢复 | 数据处理 |
|--------|------|--------|----------|
| 1 | 正常 | — | 保留 |
| 0 | 已停用 | ✅ | 保留 |
| 2 | 待注销（冷静期） | ✅ | 保留 |
| 3 | 已注销 | ❌ | 匿名化保留 |

**核心原则:** 永不物理删除，仅做匿名化（用户名改为 `deleted_<id>`、手机号/邮箱清空、密码随机化），保留记录以维持外键与审计链完整。

**功能清单**

- [ ] 停用/启用带原因（`disable(id, reason)`），记录操作人与时间
- [ ] 临时停用 `banned_until`，到期由 `@nestjs/schedule` 自动恢复
- [ ] 软删除（TypeORM `@DeleteDateColumn`）+ 回收站，支持恢复
- [ ] 新增 `account_status_logs` 表，前端用户详情抽屉展示状态变更时间线
- [ ] 批量停用，支持离职批量处理
- [ ] C 端自助注销：手机端「我的 → 设置 → 注销账号」，短信验证码二次确认 + 7 天冷静期
- [ ] 新增权限码 `system:user:restore`、`system:user:purge`（彻底删除，仅超管）

### 合规提示
`mobile/has-web` 为 C 端应用。如需上架国内应用商店，提供"账号注销"入口为审核硬性要求（《个人信息保护法》第 47 条要求个人信息处理者提供删除途径）。本项可一并补齐该合规缺口。

### 实施风险
物理删除改软删除会影响所有查询 `users` 的地方。TypeORM 软删除默认自动过滤，但手写 SQL 处需逐个检查。建议分两步：先做"停用带原因 + 状态时间线 + 软删除"，再做"C 端自助注销 + 冷静期"。
